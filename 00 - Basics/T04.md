# CLIENTE FRONT END

La mayoría de los usuarios requieren de una aplicación **off-chain** para acceder a una **dApp** a modo de User Interface (UI). Para ello existen ciertas herramientas y opciones en Solana:

### RPC Clients:
Un **RPC Client** es una biblioteca de software que permite que una aplicación de frontend se comunique con un nodo RPC de Solana. No se conecta directamente a la blockchain, sino que actúa como un intermediario, permitiendo:
* **Consultar información:** Por ejemplo, el saldo de una cuenta, los datos de un programa o el historial de transacciones.
* **Enviar transacciones:** Firmar una transacción en el frontend y enviarla al nodo RPC para que sea procesada por los validadores de la red.

Un RPC client maneja toda la complejidad de las peticiones HTTP y el formato JSON otorgando al prorgamador, métodos sencillos como *getBalance()* o *sendTransaction()*.

### Wrappers:
Un "envoltorio" o es una librería que simplifica el uso de otra librería. En el contexto de Solana, el término se usa a menudo para referirse a herramientas que simplifican el uso del **RPC client**. Por ejemplo, si el RPC client permite enviar una transacción, un wrapper podría hacer que ese proceso sea aún más sencillo, manejando automáticamente la creación de las instrucciones, la firma y el envío. Su objetivo principal es abstraer el código repetitivo (boilerplate) y las complejidades de bajo nivel para que el desarrollador pueda centrarse en la lógica de negocio. Existen diferentes **wrappers**:

* **@solana/web3.js** es la librería de **RPC client** oficial para *JavaScript/TypeScript*. Es el wrapper más popular y fundamental para que los desarrolladores web construyan interfaces de usuario (UIs) para **dApps** en Solana. Es la implementación práctica de un RPC client para el entorno web, que a su vez actúa como un wrapper para simplificar la interacción con la red de Solana.
* **Anchor's Client Library** es una librería que simplifica la interacción con programas de Anchor. Se encarga de la serialización, la validación de cuentas y el manejo de errores de forma automática, reduciendo el código repetitivo en el frontend. 
* **Solana-py** es la librería oficial de Solana para Python, utilizada para construir aplicaciones y scripts en el backend, realizar consultas, enviar transacciones y firmar mensajes fuera del navegador. No es solo un wrapper para un cliente RPC, sino que es un cliente RPC para Python equivalente a web3.js. 
* **Solana-client** es la librería cliente RPC de bajo nivel de Solana para Rust. Es muy potente y versátil, pero requiere que el desarrollador maneje muchos detalles de la transacción y la comunicación con el nodo RPC. Se usa comúnmente en la construcción de servicios de backend y herramientas de línea de comandos.
* **Solana-web3.php** es un RCP client *NO OFICIAL* para PHP, que permite a los desarrolladores de PHP interactuar con la red.
* **solana-go** es un cliente RPC para **Go**, mantenido por la comunidad, popular para servicios de backend de alto rendimiento.

## PROCEDIMIENTO

### Conexión con un Cluster:
Un **cluster** de Solana es un conjunto de validadores descentralizados que trabajan juntos para atender las transacciones de los clientes. Los principales clusters de Solana son **Devnet**, **Testnet** y **Mainnet**. En el siguiente ejemplo se define una función a la que se nombra **establishConnection()**, que se conectará a Testnet, por ser un entorno de pruebas:

    01 export async function establishConnection(): Promise<void> {
    02    const rpcUrl = 'https://api.testnet.solana.co';
    03    connection = new Connection(rpcUrl, 'confirmed');
    04    const version = await connection.getVersion();
    05    console.log('Connection to cluster established:', version);
    06 }

* **01** se define la función con las siguientes particularidades: 
    * **export** permite que esta función sea importada y utilizada en otros archivos de un proyecto de JavaScript.
    * **async** indica que la función es asíncrona, lo que significa que realizará operaciones que tardan un tiempo (como la comunicación a través de la red) y que se deben esperar **(await)**.
    * **Promise<void>** Declara el tipo de retorno de la función. En este caso, la función no devuelve ningún valor explícito, pero retorna una promesa que se resolverá cuando la conexión se establezca.
* **02** define una variable **(rpcUrl)** de tipo constante que almacena la URL del cliente RPC. Esta es la dirección del nodo al que tu aplicación se conectará. En este caso, es la URL del cluster de Testnet, la red de pruebas.
* **03** se crea **connection** como una nueva instancia del objeto **Connection** de la librería @solana/web3.js. Incluyéndo los parámetros:
    * **rpcUrl** la dirección del nodo RPC al que se debe conectar.
    * **'confirmed'** Este es el nivel de compromiso (Commitment Level). Le dice al nodo RPC qué tan "confirmada" debe estar la información que devuelva. 'confirmed' significa que el nodo solo devolverá información sobre los bloques que han sido confirmados por una supermayoría de los validadores, lo que garantiza que la información es confiable.
* **04** define la constante **version** como un **await** del método RCP **connection.getVersion()**, que consulta la versión del nodo al que se está conectando. Es decir, se detiene la ejecución de la función asíncrona hasta que la promesa de **getVersion()** se resuelva y el valor de la versión sea retornado
* **05** Esta línea imprime un mensaje en la consola del navegador, indicando que la conexión se ha establecido con éxito y mostrando la versión del nodo. Es útil para la depuración.

### Conexión con una Wallet:
Este paso es fundamental para que el usuario pueda firmar transacciones y pagar las tarifas de gas. El uso de billeteras es necesario para no exponer las claves privadas cada vez que se necesita firmar. El token SOL en **Testnet** es gratis, puede obtenerse a través de airdrop directamente en una billetera. La lectura de datos de la blockchain de Solana no se considera una transacción. Por lo que es necesario pagar tarifas tan solo para la escritura de datos.Las conexiones con billeteras pueden diseñarse desde cero, pero Solana tiene un componente de **React** predefinido que puede conectarse a una aplicación UI:

    01 import WalletConnectButton from "@solana/wallet-adapter-react-ui";
    02 export function ConnectButton() {
    03   const { autoConnect, setAutoConnect } = useAutoConnect();
    04
    05   return (
    06     <>
    07       <WalletConnectButton />
    08     </>
    09   );
    10 }

* **01** se importa un componente de React llamado **WalletConnectButton** de la librería **@solana/wallet-adapter-react-ui**. Esta librería proporciona componentes de UI (botones, modales, etc.) pre-construidos para que los desarrolladores no tengan que crearlos desde cero.
* **02** define una función nombrándola **ConnectButton()** que será un componente de React. La palabra clave **export** lo hace disponible para ser usado en otros archivos de la aplicación.
* **03** define dos constantes **autoConnect** y **setAutoConnect**, asignándoles los valores que retorna el objeto **useAutoConnect()**, que es un **Hook** de React proporcionado por la librería **@solana/wallet-adapter-react**. Un Hook es una función especial que permite "enganchar" el estado de React y el ciclo de vida de un componente funcional. Está línea desestructura el objeto para obtener dos variables: 
    * **autoConnect** es un booleano que indica si la conexión automática está habilitada y
    * **setAutoConnect** es una función para cambiar el estado de la conexión automática. 

* **05-09** La función retorna la interfaz de usuario que se renderizará en la pantalla. El <> y </> son fragmentos de React, un contenedor que permite renderizar **<WalletConnectButton />**, un botón pre-estilizado y con toda la lógica incorporada para conectar al usuario con su billetera. Al hacer clic en este botón, se activará un cuadro de diálogo de la billetera para solicitar permiso al usuario.

### Verificar el programa:
Antes de enviar una transacción, el cliente debe asegurarse que se conectará a una dApp que existe:

    01 const programInfo = await connection.getAccountInfo(programId);
    02 if (programInfo != null) {
    03   console.log('program exists');
    04 }

* **01** se define una constante llamada **programInfo** con las siguientes particularidades:
    * El método **connection.getAccountInfo(programId)** consulta al nodo RCP sobre el dato **programId** de una cuenta específica. En este caso **connection** se refiere al objeto de la clase **Connection** que el desarrollador instanció en la conexión con el cluster. 
    * La llamada a esta API es asíncrona, así que **await** es necesario para esperar la respuesta del nodo RPC.
    * Si la dApp existe en el cluster, el método retornará la **Public Key** de la cuenta programa, y la almacena en la constante **programInfo**. Pero si la dApp no existe, el valor de la constante será **null**.
* **02-03** Si el valor de la constante es distinto de **nul**, se imprime por consola que el programa existe.

### Generar la PDA:  
Ya que un programa en Solana es **stateless**, es necesaria una **Program Derived Address** para almacenar sus datos. Recordando que las PDA no tienen una clave privada, sino que su autoridad para firmar transacciones es la clave privada del programa. Inicialmente se debe derivar la dirección de la PDA:

    01 const COUNTER_SIZE = 8;
    02 const COUNTER_SEED = 'COUNTER_APP';
    03 counterPubkey = await PublicKey.createWithSeed(
    04     payer.publicKey,
    05     COUNTER_SEED,
    06     programId,
    07 );

* **01** define una constante llamada COUNTER_SIZE que se utlizará luego para especificar el tamaño de la cuenta en bytes. Es decir, el espacio que la struct de datos (MyAccount) necesitará. En este caso 8 bytes (u64)
* **02** define una constante llamada COUNTER_SEED que almacena una cadena de texto. Un seed es una serie de bytes (en este caso una cadena de texto) que se utiliza para generar una dirección de PDA de forma determinista (si le das las mismas tres entradas, siempre obtendrás la misma dirección de salida).
* **03** se define la clave pública dentro de la variable *counterPubkey* asignándole el restorno del método **PublicKey.createWithSeed()**. Es un método de **@solana/web3.js** que genera realiza un cálculo criptográfico tres valores que se incluyen como parámetros, produciendo una nueva dirección **(PublicKey)**. Esta dirección resultante no tiene una clave privada. La única forma de que un programa pueda interactuar con una cuenta en esa dirección es que el **programId** coincida con la dirección derivada. 
* **04-06** los tres parámetros qie necesita el método **createWithSeed()**:
    * **payer.publicKey**: La clave pública de la cuenta que paga por la transacción **(basePubkey)**.
    * **COUNTER_SEED**: La semilla que se definió anteriormente.
    * **programId**: La clave pública del programa que será el propietario de la cuenta.

Posteriormente a la derivación de la dirección de la PDA, se debe verificar que la cuenta no existe previamente, y en tal caso, crearla:

    01 const counterAccount = await connection.getAccountInfo(counterPubkey);
    02 if counterAccount != null {
    03   console.log('PDA exists');
    04 } else {  
    05   const transaction = new Transaction().add(
    06     SystemProgram.createAccountWithSeed({
    07       fromPubkey: payer.publicKey,
    08       basePubkey: payer.publicKey,
    09       seed: COUNTER_SEED,
    10       newAccountPubkey: counterPubkey,
    11       lamports,
    12       space: COUNTER_SIZE,
    13       programId,
    14     }),
    15   );
    16   await sendAndConfirmTransaction(connection, transaction, [payer]);
    17 }

* **01** define la constante **counterAccount** con la respuesta del método **getAccountInfo()**, que retornaría la información de la cuenta en la dirección que se derivó anteriormente **(counterPubkey)**, si es que existe.
* **02-03** si el retorno fue distinto de **null**, es decir, la clave pública existe, entonces la cuenta ya existe.
* **04-05** el caso contrario, si la cuenta no existe, se define una nueva transacción con el método **new Transaction().add()**, que puede contener una o más instrucciones, que se encierran entre paréntesis.
* **06** la instrucción que se envía en la transacción es una llamada al **SystemProgram** (programa nativo de Solana), particularmente a su método **.createAccountWithSeed()** especificando los siguientes parámetros:
    * **fromPubkey**: La cuenta que pagará por la creación de la nueva cuenta.
    * **basePubkey**: La clave pública que se utilizó para derivar la dirección de la cuenta. Debe ser la misma que la del payer.
    * **seed**: La semilla que se usó para la derivación.
    * **newAccountPubkey**: La Public Key de la nueva cuenta que se va a crear.
    * **lamports**: La cantidad de lamports que se transferirán a la nueva cuenta. Estos lamports son necesarios para cubrir el **rent-exemption** (costo de almacenamiento de la cuenta en la red).
    * **space**: El tamaño de la cuenta en bytes definido anteriormente. 
    * **programId**: El ID del programa que será el dueño de la nueva cuenta.
* **16** la función **sendAndConfirmTransaction()** de la biblioteca **@solana/web3.js** es la que realmente realiza la transacción, por ello necesita los parámetros:
    * **conection** constante creada previamente que definía la dirección del nodo RPC al que se debe enviar la transacción.
    * **transaction** es la transacción que se definió inmediatamente arriba con la instrucción de construir la PDA. 
    * **[payer]** la firma con la clave privada del pagador (payer)

    El **await** hace que el código espere hasta que la transacción sea confirmada en la cadena de bloques, garantizando que la cuenta ha sido creada con éxito.

### Obtener datos:
La aplicación de front-end puede leer los datos de una cuenta en la blockchain de Solana y convertirlos en un formato utilizable. En este caso, usando **getAccountInfo** y luego usando **Borsh** para deserializar los datos que obtiene. Este proceso es el inverso de la serialización que ocurre al escribir datos.

    01 const accountInfo = await connection.getAccountInfo(counterPubkey);
    02 const counter = borsh.deserialize(
    03   CounterSchema,
    04   CounterAccount,
    05   accountInfo.data,
    06 );
    07 console.log('counter value is :', counter.counter);

* **01** define la constante **accountInfo** que espera la respuesta del método **connection.getAccountInfo()** que consulta al nodo RPC y devuelve un objeto que contiene los detalles de la cuenta especificada mediante la clave pública  derivada anteriormente y almacenada en la constante **counterPubkey**. El objeto **accountInfo** contiene la información de la cuenta, incluyendo los datos crudos como un Buffer de bytes en **accountInfo.data**.
* **02** se define una constante **counter** que almacena un objeto JavaScriptque tiene la misma estructura que un struct de Rust. Se obtiene mediante el método obtenido de la librería de Borsh para JavaScript **(@solana/borsh)**, deserializando los parámetros: 
    * **CounterSchema**: Es el esquema de serialización. Un objeto que el desarrollador define en el front-end que describe la estructura de la struct de Rust (por ejemplo, pub counter: u32).
    * **CounterAccount**: Es la clase o tipo de JavaScript en el que se convertiran los datos.
    * **accountInfo.data**: Son los datos crudos, el Buffer de bytes que se obtuvo en el paso anterior.
* **07** después de la deserialización, la variable **counter** es un objeto de JavaScript. Se puede acceder a sus propiedades, como **counter.counter**, para obtener el valor numérico y mostrarlo por consola.

### Modifcar datos:
Es el proceso de enviar una transacción desde el front-end para invocar a un programa de Solana. El objetivo en este ejemplo es actualizar el valor del contador que está almacenado en una cuenta on-chain, para eso es necesario construir una instrucción de transacción y luego enviar esa instrucción a la red para que sea procesada. En el siguente código se crea la transacción:

    01 const instruction = new TransactionInstruction({
    02   keys: [{ pubkey: counterPubkey, isSigner: false, isWritable: true }],
    03   programId,
    04   data: Buffer.alloc(0),
    05 });

* **01** crea una constante llamada **instruction** que contiene un objeto de la clase **TransactionInstruction()**, definiendo sus parámetros:
    * **keys**: Es la lista de cuentas que el programa necesita para la instrucción. Conteniendo:
        * **pubkey**: La clave pública de la PDA del programa.
        * **isSigner**: el valor **false** indica que esta cuenta no firma la transacción. Esto es correcto para una PDA, ya que las PDAs no tienen clave privada.
        * **isWritable**: el valor **true** indica que la cuenta será modificada por el programa (se le va a escribir el nuevo valor del contador).
    * **programId**: La clave pública del programa al que se dirige esta instrucción.
    * **data**: Los datos de la instrucción. En este ejemplo, el programa asume que la única instrucción es incrementar, por lo que no se envían datos. **Buffer.alloc(0)** crea un buffer de 0 bytes.

Una vez creada la transacción, se debe enviar a la blockchain para su ejecución:

    01 connection.sendTransaction(
    02   new Transaction().add(instruction),
    03   [payer],
    04 );

* **01** es el método que envía la transacción a la red. especifica la dirección **connection** que se definió al comienzo en el cliente RPC para enviar la transacción que se detalla entre paréntesis.
* **02** crea una nueva transacción de Solana y le añade la instruction que se acaba de definir.
* **03** la transacción debe ser firmada por una cuenta que tenga saldo en SOL para pagar las tarifas de la red **([payer])** es la cuenta que firma la transacción para autorizarla.
