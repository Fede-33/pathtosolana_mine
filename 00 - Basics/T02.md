# CODE IN SOLANA
Solana es un ecosistema libre para que cualquiera pueda escribir y desplegar **On-Chain Programs** sin requerir permisos, solo pagando la renta correspondiente.

## DAPPS
Las Descentralized APPs Son el núcleo de un proyecto en Solana, ya que proporcionan la interacción entre usuarios y blockchain. Cada dApp consta de dos partes: 
* **On-Chain:** El Programa alojado en la Blockchain de Solana.
* **Off-Chain:** Es el Front-End, usualmente desplegado en un sitio web o una aplicación móvil. 

## LENGUAJES
La mayoría de los programas en Solana suelen escribirse en Rust o C++, pero puede usarse cualquier lenguaje que admita **LLVM's BPF Backend**, la tecnología de compilación que permite que el código se traduzca al formato que la máquina virtual de Solana puede ejecutar.

### Proceso de desarrollo, compilación y despliegue de programas:
1. Un desarrollador escribe un programa **on-chain** en un lenguaje de alto nivel, como Rust o C++.
2. El compilador de Rust, que utiliza la infraestructura **LLVM (Low Level Virtual Machine)**, traduce ese código a un formato intermedio. En términos simples, el frontend de LLVM es el "motor" que toma el código fuente de alto nivel y lo procesa.
3. El backend de LLVM (específicamente **LLVM BPF backend**) toma la representación intermedia, y la convierte en un **eBPF (Extended Barkeley Packet Filter)** optimizado. Este bytecode es el formato que la máquina virtual de Solana (SVM) entiende y puede ejecutar. 

    * **Solana Bytecode Format (SBF):** Solana utiliza un formato modificado basado en eBPF que se caracteriza por permitir alto rendimiento, velocidad, multiejecución de programas, mejoras de seguridad y llamas al sistema (syscalls) personalizadas para interactuar con el entorno de la blockchain. Actualmente, el código desplegado en la blockchain por los desarrolladores, se almacena en un archivo ejecutable en un formato particular de SBF llamado **ELF (Executable and Linkable Format)**. Este archivo es el que finalmente se almacena en la cuenta programa.

4. Interactuar con el **on-chain program** usando el **JSON-RPC API** de Solana.
    * **JSON-RPC (JavaScript Object Notation -  Remote Procedure Call):** Es un protocolo que permite a una aplicación ejecutar una función o método en un nodo de Solana. Tanto la solicitud, como la respuesta, están en formato JSON. 


## RUST
Es un lenguaje open-source, de alto rendimiento, tipado estático y eficiente en cuanto al uso de memoria. Resultando confiable, rápido y seguro para el desarrollo en Solana.

### Entrypoint:
Cómo en todos los programas, en Solana se debe definir un punto de entrada que indique al runtime dónde empezar a ejecutar el código. Para una Program Account simple, que solo contenta un "Hello World!", el código sería el siguiente:

    01 entrypoint!(process_instruction); 
    02
    03 pub fn process_instruction(
    04    program_id: &Pubkey,
    05    accounts: &[AccountInfo],
    06    instruction_data: &[u8]
    07 ) -> ProgramResult {
    08    msg!("Hello World!");
    09    Ok(())
    10    }

* **01** La macro **entrypoint!** declara la función **process_instruction** como función principal. Cuando un validador ejecute el programa, comienza a ejecutar por esta función.
* **03** Definición de la función **process_instruction**, con los parámetros estándar que todo programa de Solana requiere para ser invocado:
    * **04** **Program_id** con una referencia a la clave pública del programa.
    * **05** **Accounts** con una referencia a un array que contiene todas las cuentas involucradas en la ejecución.
    * **06** **instruction_data** con una referencia a un array de binarios de 8 bits, que compondrán el código en **Solana Bytecode Format** que puede ser ejecutado por la **SVM**. En este caso, ese array está vacio porque el programa no procesa nada.
* **07** Se declara el resultado del programa.
* **08** Otra macro que imprime un mensaje de depuración en los registros de la transacción en el validador. Si bien se registra en la blockchain, no se almacena en ninguna cuenta. Es muy útil para depuración y verificación durante la ejecución de un programa.
* **09** **Ok(())** es la forma de Rust de indicar que la función se completó con éxito, es el valor que retorna **ProgramResult** cuando no hay errores. Entonces, finaliza la ejecución considerándola exitosa.

### Plantilla básica:
El template general escrito en Rust que sirve como un punto de partida para cualquier dApp o programa on-chain que quieras crear:

    01 use solana_program::{
    02     account_info::{AccountInfo},
    03     entrypoint,
    04     entrypoint::ProgramResult,
    05     msg
    06 };
    07 
    08 entrypoint!(process_instruction);
    09
    10 pub fn process_instruction(
    11     program_id: &Pubkey,
    12     accounts: &[AccountInfo],
    13     instruction_data: &[u8], 
    14 ) -> ProgramResult {
    15     msg!("program starts here");
    16 
    17     Ok(())
    18 }

* **01** Importaciones de la biblioteca **solana_program**, conocida como **Solana Program Crate**, que contiene las herramientas necesarias para construir un programa que pueda ejecutarse en la blockchain.
    * **02** Importa la estructura **AccountInfo**, que es la forma en que el programa interactúa con las cuentas de Solana. Cada cuenta que un programa necesita para operar (leer o escribir datos) se pasa a través de una AccountInfo.
    * **03** Importa el macro **entrypoint!** que se utiliza para indicarle al compilador de Rust cuál es la función que debe ser llamada cuando el programa se invoca.
    * **04** Importa type **ProgramResult**, un tipo de resultado (Result) específico de Solana que se utiliza para manejar errores.
    * **05** Importa la macro msg!, que se utiliza para imprimir mensajes en los logs de la transacción. Es muy útil para depurar el código y ver el progreso de la ejecución de un programa.
* **08** Esta línea utiliza la macro entrypoint! para designar a la función **process_instruction** como el punto de entrada del programa. 
* **10** La función principal que contiene la lógica del programa. Recibe tres argumentos principales:
    * **11** la **Public Key** del propio programa que se está ejecutando. Se utiliza para verificar la propiedad de las PDAs. 
    * **12** una lista de todas las cuentas que la transacción ha pasado al programa. Si tu programa necesita modificar una PDA o leer datos de una cuenta, esa cuenta debe ser incluida en esta lista.
    * **13** datos que se envían efectivamente al programa en su invocación, los parámetros necesarios para que ejecute la lógica correcta
* **14** determina cuál será la lógica del programa.
    * **15** la macro **msg!** imprime el mensaje "program starts here" en los logs de la transacción. Es la primera acción que realiza el programa al ser llamado, y es una práctica común para confirmar que el programa se ha ejecutado correctamente. En una programa real, aquí comenzaría todo el código que necesita ser ejecutado.
    * **17** finalmente, la función retorna Ok(()). En Rust, **Ok** indica que la operación se completó sin errores. El () representa una tupla vacía, y en este contexto, significa que la función no retorna ningún valor. Si ocurriera un error, la función retornaría **Err(ProgramError::...)**.

### Modelos de Datos:
En el desarrollo de programas de Solana, es una buena práctica definir la estructura de los datos que se van a almacenar en las cuentas. En lugar de tratar los datos como un montón de bytes **(&[u8])**, se modelan con forma de **structs** de Rust. Esto hace que el código sea más legible, seguro y fácil de mantener. El siguiente modelo almacena solo un dato, un contador:

    01 use borsh:: {BorshDeserialize, BorshSerialize};
    02 
    03 #[derive(BorshSerialize, BorshDeserialize, Debug)]
    04 pub struct CounterAccount {
    05     pub counter: u32,
    06 }

* **01** Importa los traits **BorshDeserialize** y **BorshSerialize** de la biblioteca **Borsh**. Es un formato de serialización que convierte las estructuras de datos de Rust en una secuencia de bytes y viceversa, puesto que los datos de una cuenta en la blockchain siempre se almacenan como bytes, por lo que necesitas una forma de convertir tu struct en bytes para guardarla **(BorshSerialize)** y de convertir los bytes de la cuenta en tu struct para leerla **(BorshDeserialize)**.
* **03** la macro de Rust **derive** implementa los traits de **Borsh** en el bloque de código que se defina a continuación
* **04** define la struct pública llamada **CounterAccount**, esta es el modelo de datos.
    * **05** es un campo público dentro de la estructura, nombrado **counter** y su tipo es **u32**. Este es el dato que se va a almacenar en la cuenta de Solana.

## Obtener detalles de Cuentas:
Después de haber definido la lógica de tu programa, el siguiente paso es acceder a las cuentas que la transacción le ha proporcionado. El programa debe iterar sobre la lista de cuentas para obtener la que necesita para su lógica. El siguiente ejemplo, invoca **next_account_info** para obtener la primera cuenta de la lista.

    01 let accounts_iter = &mut accounts.iter();
    02
    03 let account = next_account_info(accounts_iter)?;

* **01** Iterar sobre las cuentas es mucho más seguro que indexar. Usar índices como accounts[0] puede ser peligroso porque, si la lista de cuentas es más corta de lo esperado, causaría un error de pánico en el programa (panic), haciendo que la transacción falle. Un iterador maneja esto de forma más segura. **let accounts_iter = &mut accounts.iter();** 
    * **accounts:** Esta es la lista de cuentas que el programa recibe como argumento **(&[AccountInfo])**.
    * **.iter():** Este método crea un iterador sobre la lista de cuentas. Un iterador es una forma de recorrer una colección de elementos sin tener que preocuparse por los índices.
    * **&mut:** Esto crea una referencia mutable al iterador. Es mutable porque cada vez que llamas a **next_account_info**, el iterador "avanza" al siguiente elemento, lo que se considera un cambio de estado.
* **03** en la siguiente línea **let account = next_account_info(accounts_iter)?;**
    * **next_account_info:** Esta es una función helper (de ayuda) que forma parte de la biblioteca de Solana y simplifica el proceso de obtener la siguiente cuenta del iterador.
    * **accounts_iter:** Le pasas el iterador que creaste en la línea anterior.
    * **?:** El operador ? es un atajo de Rust para el manejo de errores. Si la llamada a **next_account_info** falla (por ejemplo, si no hay más cuentas en el iterador), el programa termina y devuelve un error. Si tiene éxito, devuelve la cuenta.
    * **let account:** Si la operación es exitosa, la primera cuenta de la lista se asigna a la variable account, que ahora es una referencia a la estructura **AccountInfo**.

### Validación:
Antes de que el programa intente leer o escribir datos en una cuenta, debe confirmar que es el propietario legítimo de esa cuenta. Validar la propiedad asegura que un programa solo interactue con los datos que se supone que debe manejar, manteniendo así la integridad y la seguridad del sistema.

    01 if account.owner != program_id {
    02    msg!("account does not have the correct program id");
    03    return Err(ProgramError::IncorrectProgramId);
    04 }

* **01** es la condición principal de la verificación, compara si el propietario de la cuenta (account.owner) es diferente al ID del programa que está ejecutando el código (program_id)
    * **account.owner:** Es la clave pública del propietario de la cuenta que se está validando. Si la cuenta es una PDA, su propietario será un programa, si es una cuenta de usuario, el propietario es el System Program.
    * **program_id:** Es la clave pública del programa que se está ejecutando actualmente. Esta es una de las variables que se le pasa a la función **process_instruction** del programa.
* **02** Si la condición es verdadera (la cuenta no es propiedad del programa), se utiliza la macro msg! para imprimir un mensaje en los logs de la transacción, lo que ayuda a la depuración.
* **03** puesto que el programa no es el propietario de la cuenta, el **return** finaliza la ejecución completa del programa, devolviendo un error de tipo **ProgramError::IncorrectProgramId**. La transacción que intentó ejecutar el programa fallará, y no se realizará ninguna modificación en la blockchain.

### Cambio de estado:
En el contexto de Solana, **cambio de estado** se refiere a modificar los datos de una cuenta, puesto que al actualizar la información de una cuenta, se actualiza el **estado de red**, que es la sumatoria de todas las cuentas. Este paso siempre debe realizarse luego de la validación de propiedad del ejemplo anterior. El siguiente código de ejemplo, muestra el proceso para leer los datos de la cuenta, modificar el valor del contador e inmediatamente guardar los cambios de nuevo en la cuenta:

    01 let mut counter_account = CounterAccount::try_from_slice(&account.data.borrow())?;
    02 counter_account.counter += 1;
    03 counter_account.serialize(&mut &mut account.data.borrow_mut()[..])?;

* **01** Se crea una nueva variable **counter_account** de tipo **CounterAccount** para almacenar la estructura deserializada. Es una variable mutable, ya que permite modificar el valor del contador en el siguiente paso.
    * **try_from_slice(...)** es un método proporcionado por la trait **BorshDeserialize** que toma los bytes de los datos y los convierte en la estructura **CounterAccount**. En este punto, los datos de la cuenta están cargados en la memoria del programa.
    * **account.data.borrow():** El **account.data** es un **RefCell** en Rust, un tipo de envoltura que te permite acceder a los datos de la cuenta de forma segura. El método **.borrow()** pide una referencia inmutable a los datos.
* **02** es la lógica principal del programa. Accede al campo **counter** de la estructura y lo incrementa en 1. En este momento, la modificación solo existe en la memoria del programa, no ha sido guardada en la blockchain.
* **03** el método **.serialize()**, proporcionado por la trait **BorshSerialize**, toma la estructura **counter_account** que acaba de ser modificada y la convierte de nuevo en bytes.
    * **&mut &mut account.data.borrow_mut()[..]** es una sintaxis de Rust un poco compleja, pero básicamente le dice a la función serialize que escriba los bytes directamente en el espacio de datos de la cuenta en la que está trabajando. El **[..]** garantiza que se utilice todo el espacio de datos disponible.
